# validate-mixology-mvp

## 为什么要做

桌面挂机基础体验成立之后，MaoMaoClub 需要单独验证调酒是否能形成经营策略。这个 MVP 关注的不是“顾客能不能买酒”，而是“玩家能不能通过材料、研发和今日菜单改变客群与收益”。

这个 MVP 要回答的问题是：

- 顾客掉落材料是否能驱动玩家继续接待特定客群？
- 研发新酒是否能形成明确目标？
- 今日菜单是否能改变顾客出现、消费或停留结果？
- 玩家是否能看出“我调整了酒单，所以经营结果变了”？

## 改动内容

- 新增“调酒经营体验”规格，用来定义第二个 MVP 的玩家可见行为。
- 定义三类 MVP 顾客与三种材料的对应关系。
- 定义材料掉落概率随接待次数增长，并设置上限，避免关键材料长期不掉落。
- 定义用材料研发新酒的流程。
- 定义今日菜单最多放入 10 种已解锁酒水。
- 定义酒水对顾客吸引、客单价、停留时间或消费结果的影响。
- 定义从顾客消费到材料掉落，再到研发酒水、调整菜单、改变客群与收益的完整验证闭环。

## 落地方式

1. 数据落地：先建立顾客、材料、酒水、今日菜单的轻量数据结构，保证后续能用配置扩展。
2. 材料闭环：在顾客离开时根据顾客类型计算掉落；同类顾客接待次数越多，对应材料掉落概率越高。
3. 研发闭环：提供调酒研发界面或临时 MVP 面板，展示材料库存、可研发酒水、研发消耗和解锁结果。
4. 菜单闭环：提供今日菜单配置，允许玩家把已解锁酒水加入菜单，最多 10 种。
5. 经营反馈：让菜单影响至少一种结果，例如特定顾客权重、订单金币、停留时间或消费倍率。
6. 对比验收：提供本轮或昨日的客群/收益摘要，让玩家能看出调整菜单前后的变化。

## 影响范围

- 规格：`mixology-experience`
- 未来代码：`features/mixology/`、`features/customers/`、`features/economy/`、调酒研发与今日菜单 UI
- 验证：确定性模拟检查顾客权重和收益变化，并在 Godot 4.6.3 中手动试玩完整调酒闭环

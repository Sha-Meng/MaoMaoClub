## ADDED Requirements

### Requirement: 调酒内容注册表

系统 MUST 以稳定且唯一的 `StringName` ID 注册器具、原料、陈列分区、槽位、交互策略、配方和酒杯定义；所有定义 MUST 在进入 CatBar 前完成类型、范围、引用和重复 ID 校验。

#### Scenario: 加载合法内容目录

- **WHEN** 内容目录包含引用完整且 ID 唯一的首批定义
- **THEN** 注册表按稳定 ID 提供只读定义查询
- **AND** 同一配置在不同运行中得到相同注册结果

#### Scenario: 配置引用未知策略

- **WHEN** 原料或器具配置引用未注册的交互策略 ID
- **THEN** 校验报告定义路径、字段和未知 ID
- **AND** 系统不会以无反馈的空交互替代该策略

#### Scenario: 配方引用缺失内容

- **WHEN** 配方步骤引用不存在的原料、器具或目标杯型
- **THEN** 该配方被标记为不可用
- **AND** 其他合法配方仍可加载并明确显示诊断结果

### Requirement: 可配置陈列分区与槽位

调酒台 MUST 通过分区与槽位配置摆放内容；每个分区 MUST 定义稳定 ID、允许类别、排序和布局锚点，每个槽位 MUST 最多容纳一个可交互内容实例。

#### Scenario: 构建首批调酒台

- **WHEN** CatBar 加载默认工作台配置
- **THEN** 酒液、冰块、香料、器具和酒杯分别出现在可识别的配置分区
- **AND** Shake 杯、长柄勺、量酒杯及首批原料都能通过稳定 ID 定位

#### Scenario: 内容放入不兼容分区

- **WHEN** 配置尝试把酒液放入只允许器具的槽位
- **THEN** 内容校验失败并指出分区与内容 ID
- **AND** 运行时不会静默改变类别或覆盖其他槽位

### Requirement: 策略化交互命令

点击、长按和拖拽输入 MUST 被转换为带主体、目标、手势、剂量与输入指标的调酒命令；会话 MUST 在应用命令前校验状态、能力标签、容量和目标规则，并 MUST 以全有或全无方式更新业务状态。

#### Scenario: 合法命令提交

- **WHEN** 玩家在允许状态对兼容目标执行配置手势
- **THEN** 对应策略一次性更新调酒组成或动作指标
- **AND** 会话追加一条不可变步骤日志并发出成功反馈

#### Scenario: 非法目标交互

- **WHEN** 玩家尝试把原料作用到不兼容器具或已满容器
- **THEN** 命令被拒绝并返回可展示原因
- **AND** 库存、容器组成和步骤日志均不发生部分修改

### Requirement: 首批原料交互

首批产品内容 MUST 至少提供酒液、冰块和香料三类原料，并 MUST 分别实现加液、逐块投冰和按份撒料的差异化交互；剂量、库存消耗和反馈 MUST 来自配置。

#### Scenario: 点击酒瓶加液

- **WHEN** 玩家点击已启用酒瓶且当前存在兼容接收容器
- **THEN** 系统向业务组成加入配置的液体剂量
- **AND** 流体适配层从容器开口播放对应加液表现

#### Scenario: 点击冰盒投冰

- **WHEN** 玩家点击冰盒且接收容器未达到冰块与容量上限
- **THEN** 系统只加入配置数量的冰块
- **AND** 每块冰作为可与杯壁和其他冰块碰撞的表现实例进入容器

#### Scenario: 点击香料撒料

- **WHEN** 玩家点击香料且当前配方步骤允许向目标容器调味
- **THEN** 系统加入配置的一份香料并记录次数
- **AND** 香料使用不同于连续液体的离散撒料反馈

### Requirement: 首批器具交互

首批产品内容 MUST 至少提供 Shake 杯、长柄勺和量酒杯，并 MUST 让器具能力而非具体场景路径决定可执行的量取、搅拌、封盖、Shake 与倒酒动作。

#### Scenario: 使用量酒杯量取

- **WHEN** 玩家选择空量酒杯后点击兼容酒瓶
- **THEN** 酒液先进入量酒杯并受其容量约束
- **AND** 玩家将量酒杯作用于 Shake 杯后才把已量取剂量提交到 Shake 杯

#### Scenario: 使用长柄勺搅拌

- **WHEN** 玩家在开放容器内以长柄勺执行满足阈值的环形拖拽
- **THEN** 系统累计搅拌时长、方向与强度指标
- **AND** 普通点击不会被误判为完成搅拌

#### Scenario: 器具后续扩展

- **WHEN** 开发者新增一个合法器具 Resource 并注册其已有交互策略
- **THEN** 工作台可以通过槽位配置展示并使用该器具
- **AND** 不需要修改 CatBar 场景控制器的器具 ID 分支

### Requirement: 显式调酒会话状态

系统 MUST 使用显式状态管理空闲、准备、Shake、倒酒、评价、待送达、已送达和取消；每个状态 MUST 只允许白名单命令，且一次订单最多存在一个活动会话。

#### Scenario: 开始订单调酒

- **WHEN** 有有效订单和配方且当前没有活动会话
- **THEN** 系统创建拥有唯一会话 ID 的空容器业务状态
- **AND** 进入准备状态并启用配置允许的工作台交互

#### Scenario: 非法状态转换

- **WHEN** 倒酒尚未完成时外部请求直接标记已送达
- **THEN** 状态机拒绝转换并记录诊断
- **AND** 订单和经济状态不结算

#### Scenario: 安全取消会话

- **WHEN** 玩家在成品提交前确认取消
- **THEN** 会话进入取消状态并清理临时容器、输入捕获和粒子表现
- **AND** 同一订单可按配置重新开始而不会继承旧步骤

### Requirement: 鼠标拖拽 Shake

Shake 杯 MUST 在加入内容并封盖后接受按住鼠标左键的二维往复拖拽，MUST 复用现有 Shake 容器的位移钳制、封闭约束、冰块碰撞和结束静稳能力，并 MUST 记录可配置的持续时间、路程、方向反转和速度指标。

#### Scenario: 有效 Shake

- **WHEN** 玩家封盖后进入 Shake 状态并持续执行位于目标区间的往复拖拽
- **THEN** 杯体在最大位移和转角内响应鼠标运动
- **AND** 液体与冰块保持在封闭杯中
- **AND** 会话记录满足配方评价的 Shake 指标

#### Scenario: 未封盖尝试 Shake

- **WHEN** 玩家在 Shake 杯未封盖时请求开始 Shake
- **THEN** 系统拒绝进入 Shake 状态并提示先封盖
- **AND** 不捕获鼠标拖拽

#### Scenario: 结束 Shake

- **WHEN** 玩家完成 Shake 并退出该状态
- **THEN** 杯体返回基准位置且运动历史被清理
- **AND** 液体与冰块在配置窗口内进入稳定表现

### Requirement: 倒酒与成品评价

系统 MUST 要求玩家把容器内容倒入兼容目标酒杯后再评价成品，并 MUST 根据确定性业务组成、步骤顺序、器具动作、Shake/搅拌指标、目标杯型和失败标签输出结构化 `DrinkResult`。

#### Scenario: 完成标准配方

- **WHEN** 玩家按配方容差完成原料剂量、必要动作并把内容倒入正确酒杯
- **THEN** 系统输出包含配方 ID、有效性、0–100 品质、标签和差异列表的结果
- **AND** 会话进入待送达状态

#### Scenario: 可饮用但不完美

- **WHEN** 成品包含全部核心成分但剂量或动作处于可接受容差外
- **THEN** 系统输出较低品质和具体偏差标签
- **AND** 配置允许时成品仍可进入待送达状态

#### Scenario: 未倒入酒杯

- **WHEN** 玩家尝试在内容仍位于 Shake 杯时结束制作
- **THEN** 系统拒绝评价为可交付成品
- **AND** 提示选择兼容酒杯并完成倒酒

### Requirement: 业务计量与粒子表现解耦

调酒结果、剂量和存档 MUST 以确定性的业务状态为准；`particle_fluid_2d` MUST 只通过公开适配器接收表现命令和提供只读诊断，粒子数量或渲染档位变化 MUST 不改变业务配方结果。

#### Scenario: 降低粒子表现档位

- **WHEN** 两次会话执行相同命令序列但使用不同粒子数量档位
- **THEN** 两次会话得到相同业务成分、步骤日志和配方评价
- **AND** 仅视觉平滑度和模拟性能可能不同

#### Scenario: headless 业务测试

- **WHEN** 测试不创建 Viewport 或粒子渲染器而执行完整命令序列
- **THEN** 会话仍可完成状态转换、配方评价和交付数据生成
- **AND** 不要求访问流体核心的可写粒子数组

### Requirement: 成品只交付一次

待送达结果 MUST 绑定订单 ID、会话 ID 和目标卡座 ID，并 MUST 具备幂等提交保护；只有有效送达事件才能把会话标记为已送达。

#### Scenario: 重复收到送达回调

- **WHEN** 同一会话因动画回调与超时保护收到两次送达请求
- **THEN** 系统只接受第一次合法提交
- **AND** 第二次请求不重复结算订单或奖励

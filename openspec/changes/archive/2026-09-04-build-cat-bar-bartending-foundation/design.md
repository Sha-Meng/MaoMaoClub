## Context

MaoMaoClub 当前以 `app/main.tscn` 装配桌面酒馆占位循环，已经具备基础顾客/猫演员、经济状态、`ConfigFile` 存档，以及独立的 `cocktail_shaker_lab` 和可复用 `particle_fluid_2d`。现有 Shake Lab 证明了加液、加冰、封盖、二维鼠标摇杯和静稳，但它是开发测试场景，不包含订单、器具/原料陈列、配方、成品评价、镜头、送酒或产品 UI。

本变更面向 Windows、Godot 4.7.1 stable。参考图提供暖暗木质像素酒吧、轻俯视全景、吧台近景、分区陈列和猫调酒师动作方向；它不是可直接发布的资产授权证明。首轮实施应以可替换占位素材完成一条纵向切片，同时保证后续新增原料、器具、配方、客人和微信内容主要通过 Resource 配置完成。

状态所有权约定如下：调酒会话拥有杯中内容、步骤日志和评价；卡座循环拥有座位与氛围顾客；微信领域状态拥有联系人、消息和朋友圈实例；`SaveService` 只负责版本化序列化，不解释业务；场景与 UI 只订阅信号并呈现状态。跨功能只传稳定 ID 和不可变快照，不传长期 Node 引用。

## Goals / Non-Goals

**Goals:**

- 交付可独立运行的 `CatBar` 场景与一次“进入调酒近景 → 制作 → 倒杯 → Neko 送达”的完整纵向切片。
- 让器具、原料、陈列槽位、交互策略、配方、酒杯、顾客表现和微信内容拥有稳定 ID、校验规则和可扩展配表。
- 把已有 Shake/粒子流体能力包装为产品适配器，保留底层模块的独立性和测试能力。
- 建立互斥且可恢复的场景模式、输入路由、镜头切换和手机 UI 层级。
- 让随机消息与朋友圈可复现、只生成一次并可保存，后续外围事件可以安全地解锁朋友和推送内容。
- 为像素素材、配置、运行时代码、测试与美术源文件建立清晰目录和验收门禁。

**Non-Goals:**

- 首轮不制作参考图中全部酒瓶、酒杯、家具和角色动画，只交付代表性内容与替换接口。
- 首轮不模拟真实流体化学、酒精度、温度扩散、每滴体积或完整酒吧经营数值平衡。
- 卡座顾客首轮不参与碰撞寻路、排队、点单谈判或复杂社交 AI；其职责是持续氛围表现。
- 微信首轮不实现自由文本聊天、语音/视频、支付、群聊、评论回复树、联网或真实系统通知。
- 打车、小红书、拍照等手机应用仅保留禁用入口/扩展槽位，不在本变更实现。
- 不在本变更升级引擎、引入第三方插件或重写 `particle_fluid_2d` 数值核心。

## Decisions

### 1. CatBar 使用“世界、调酒工作台、外围 UI”三层组合场景

`features/cat_bar/cat_bar.tscn` 以 `Node2D` 世界为主，包含全景背景、吧台热点、卡座座位点、Neko 和氛围演员；一个产品级 `Camera2D` 在 `OVERVIEW` 与 `MIXING_CLOSEUP` 两个具名构图预设间 Tween。调酒工作台是随近景启用的独立子场景，手机外壳和微信位于高层 `CanvasLayer`，不受相机缩放影响。

选择单场景分层，而不是在全景和调酒间切换两个主场景，是为了保持卡座氛围、Neko、音乐和当前订单连续。工作台仍是可独立 F6 运行的嵌套场景，便于测试。手机 UI 的非交互装饰节点使用 `MOUSE_FILTER_IGNORE`，模态面板开启时由统一输入路由截断世界交互，避免透明 `Control` 吃掉点击。

### 2. 以两个显式状态机约束流程，不让 UI 按钮拼接业务

场景模式状态机使用 `OVERVIEW`、`ENTERING_MIXING`、`MIXING`、`SERVING`、`PHONE_OPEN` 和 `RETURNING_OVERVIEW`。调酒会话状态机使用 `IDLE`、`PREPARING`、`SHAKING`、`POURING`、`EVALUATING`、`READY_TO_SERVE`、`DELIVERED`、`CANCELLED`。状态转换由控制器验证并发出过去式信号；表现层只能提交命令，不能直接改状态。

手机从全景或允许暂停的调酒节点打开时，输入路由保存前一模式并恢复；默认在 `SHAKING`、`POURING` 和 `SERVING` 中拒绝打开，避免拖拽丢失与动画状态破坏。未来若希望手机完全暂停世界，只需替换模式策略而不改微信领域模型。

### 3. 内容定义用 Resource，运行时状态用 RefCounted/快照，行为用策略注册表

配置类按职责拆分：

- `ToolDefinition`：`tool_id`、显示资源、能力标签、允许手势、目标规则和反馈 ID。
- `IngredientDefinition`：`ingredient_id`、类别、默认剂量、流体/固体/香料参数、交互策略 ID、库存规则和表现资源。
- `StationZoneDefinition` / `StationSlotDefinition`：分区 ID、槽位 ID、布局锚点、排序、允许类别与初始内容。
- `InteractionDefinition`：手势类型、阈值、持续时间、剂量规则、前置/目标标签、反馈和失败原因。
- `RecipeDefinition`：配方步骤、容差、允许替代、目标杯型和评价权重。
- `GlassDefinition`、`PatronArchetypeDefinition`、`WechatContactDefinition`、`WechatMessageTemplate`、`WechatMomentTemplate`：各自的可编辑内容。

Resource 只保存静态数据且不持有场景 Node。运行时使用 `BartendingSessionState`、`DrinkCompositionSnapshot`、`WechatState` 等对象；从共享 `.tres` 读取后不原地修改。`InteractionExecutorRegistry` 以 `StringName` 策略 ID 映射到小型 `RefCounted` 执行器，首批包含 `pour_fixed_dose`、`drop_ice`、`sprinkle`、`measure`、`stir_drag`、`seal_toggle`、`shake_drag`、`strain_pour`。选择注册表而不是为每种素材写脚本，可让内容配置与代码扩展分离，同时对未知策略给出启动时错误。

### 4. 所有交互先形成命令，再以事务方式提交到会话

点击/拖拽被标准化为 `InteractionCommand`，包含主体 ID、目标 ID、手势、剂量、时间戳和输入指标。会话先校验当前状态、目标能力、库存/容量和配方约束，再一次性应用并追加不可变步骤日志；失败命令不产生半完成状态。

首批体验约定为：酒瓶单击向当前接收容器倒入配置剂量；冰盒单击投入一块冰；香料单击加入一撮；量酒杯先选择接收、再点击酒瓶量取、再点击 Shake 杯倾倒；长柄勺在杯内持续环形拖拽累计搅拌；Shake 杯通过封盖后按住左键往复拖拽累计强度；完成后拖向或点击目标酒杯执行过滤倒酒。所有剂量和阈值都来自配置，后续可增加长按连续倒、鼠标滚轮控量或触屏手势而不改变配方模型。

### 5. 产品调酒适配已有流体模块，但规则与模拟解耦

`MixingVesselAdapter` 负责把业务命令转换为现有加粒子、冰块、容器运动和快照调用。调酒会话的判定依据是确定性的业务组成和步骤日志；粒子流体负责视觉/运动反馈，不作为唯一计量来源。这样即使性能档位降低粒子数，配方体积、得分和存档仍保持一致，也能在 headless 测试中不用 Viewport 完成业务验证。

Shake 评分使用时间窗口内归一化的拖拽路程、方向反转次数、峰值速度和持续时间，配置成目标区间；不会鼓励无限高速甩鼠标。适配器继续遵守现有最大位移、封盖约束和结束静稳逻辑。

### 6. 配方评价输出结构化结果，并以送达作为订单提交点

`RecipeEvaluator` 比较成分剂量、顺序、必要器具动作、Shake/搅拌指标、目标酒杯与溢出/遗漏，输出 `DrinkResult`：配方 ID、有效性、0–100 品质、标签、差异列表和成品外观快照。首轮允许“可饮用但不完美”的结果继续送达；缺少核心成分、未倒入酒杯或会话非法才阻止交付。

Neko 通过预设 `Marker2D` 路径和动画状态完成“取杯 → 走到目标卡座 → 放杯 → 返回”，无需为固定室内动线引入导航。只有 `drink_delivered` 后，`mixology-experience` 才结算订单、奖励与外围内容触发；动画被跳过或降级时仍必须在受控超时后完成逻辑提交。

### 7. 卡座氛围使用座位租约和对象池，不介入核心订单

`PatronAmbienceController` 维护有限座位点和顾客表现对象池。每位氛围顾客按“进入 → 入座 → 饮用 → 离开”时间线运行，持有座位租约；无空位时延迟生成，不叠放演员。随机选择由场景种子与序列号驱动，最大活跃数、生成区间、停留时间和动画变体均可配置。

首轮将氛围顾客与可服务订单顾客视为不同角色，防止纯表现循环意外改变经济。后续可以用稳定 `patron_instance_id` 把某个氛围顾客提升为订单顾客。

### 8. 微信随机内容是“模板生成实例”，打开页面不会重新抽取

手机壳 `PhoneShell` 管理应用入口、返回栈和角标；`WechatService` 管理领域状态，三个页签分别消费只读列表模型。联系人由稳定 ID 定义，初始解锁店长猫、打工猫、酒吧常客名菜。消息与朋友圈使用带作者条件、内容标签、权重、图片槽位、互斥键和冷却的模板生成实例。

生成器使用保存的基础种子与递增游标，响应“新一天、完成订单、认识顾客、外围事件”等领域事件；生成后的文本、作者、图片 ID 和时间戳作为实例保存，切页或重开手机不会重抽。朋友圈首批支持头像、文案、0–若干张配置图片、时间标签和内容类别，不实现评论树。UI 列表采用可回收条目或受控上限，避免无限 Node 增长。

### 9. 存档升级为分区、版本化快照

`SaveService` 保留 `ConfigFile`，将版本从 1 升到 2，并新增 `bartending`、`phone_wechat` 和 `content_unlocks` 分区。领域服务各自提供 `to_save_data()` / `restore_from_save()`；加载使用 `.get(key, default)`、类型/范围校验和稳定 ID 过滤。随机数只保存种子与游标，已展示内容保存完整实例，避免算法调整改写历史。

迁移 v1 时保留经济与窗口字段，补齐默认调酒进度、三个初始联系人、空消息/朋友圈或首启引导内容。写入继续使用 `user://maomao_club_save.cfg`，本变更不保存 Node、Texture 或 Resource 实例。

### 10. 目录、资产和配置按功能与生命周期分离

建议落点：

```text
features/
  cat_bar/
    cat_bar.tscn
    cat_bar_controller.gd
    camera/
    bartending/{domain,config,configs,interaction,presentation,adapters}/
    patrons/{domain,config,configs,presentation}/
  phone/
    shell/
    wechat/{domain,config,configs,presentation}/
assets/
  cat_bar/{environment,characters,tools,ingredients,glassware,ui,wechat}/
art_source/
  cat_bar/                 # .gdignore，仅保存可编辑源文件与授权说明
tests/
  cat_bar/{unit,integration,visual}/
  phone_wechat/{unit,integration}/
```

文件/目录使用 `snake_case`，节点使用 `PascalCase`。像素纹理默认关闭过滤与 mipmap，使用整数基准分辨率、整数缩放和一致的 pixels-per-unit；运行时只引用导入成品，不引用 `art_source`。每个资产清单记录稳定 ID、用途、作者/来源、许可、原始尺寸、锚点、动画帧与替换状态。参考图仅进入设计参考清单，不复制为发布纹理。

### 11. 验证分为纯逻辑、场景集成、视觉和性能四层

纯逻辑测试覆盖注册表/配置校验、会话转换、交互事务、配方评价、随机生成确定性和 v1→v2 迁移；集成测试完成一次标准配方并断言送达后才结算；场景冒烟测试验证 CatBar F6、相机往返、手机返回栈和输入互斥；视觉清单检查像素抖动、遮挡、半透明杯液位、陈列可读性与手机安全区域。

目标为 60 FPS、固定物理 tick 60；CatBar 产品场景采用配置化粒子预算，常规近景以现有实测档位为上限，手机打开和全景模式不无谓运行不可见的高成本流体模拟。测试入口以进程退出码表示成功/失败。

## Risks / Trade-offs

- [变更跨度包含场景、玩法、UI、内容和存档，实施时间长] → 按任务阶段建立可运行门禁，每阶段都保留可演示纵向切片，最后才扩充内容量。
- [粒子流体视觉结果与业务计量漂移] → 业务组成/评分使用独立确定性模型，流体只消费命令并提供表现快照。
- [策略 ID 提供扩展性但可能配置错误] → 启动时集中校验未知 ID、目标标签、循环依赖、重复稳定 ID 和缺失资源；发布构建把错误视为门禁失败。
- [相机 Tween、手机模态层和拖拽输入互相抢占] → 单一模式状态机与 InputRouter 持有输入焦点，状态切换时显式取消捕获并清理悬停/拖拽状态。
- [朋友圈随机内容容易重复、矛盾或无限增长] → 模板互斥键、冷却、权重、每类上限、保存游标与列表容量共同约束，旧条目按策略归档而非每帧生成。
- [在 ConfigFile 中保存大量朋友圈实例会膨胀] → 首轮设置受控历史上限；规模超过阈值时再迁移到独立二进制/JSON 数据文件，不提前复杂化。
- [像素素材尺寸/锚点不一致导致跳帧和错位] → 资产清单与导入校验工具固定网格、pivot、过滤和帧尺寸；视觉测试使用代表性场景截图。
- [参考图来源/授权不明确] → 仅作为风格参考，发布素材必须具备原创或明确许可记录。
- [固定路径送酒在布局变化后失效] → 路径由具名 Marker 和卡座配置生成并校验；只有出现动态障碍需求时才升级到 NavigationServer2D。

## Migration Plan

1. 先增加数据类、注册表、配置校验和 v2 默认存档，不切换主场景；验证旧 v1 存档可加载。
2. 将现有 Shake Lab 能力包在 `MixingVesselAdapter` 后，保持原实验场和回归测试继续通过。
3. 建立可 F6 的 CatBar 占位场景、镜头和工作台，完成代表性配方纵向切片。
4. 接入 Neko 送酒、订单提交与卡座氛围，再接入手机壳和微信三页签。
5. 通过功能开关将 `app/main.tscn` 从占位 TavernLoop 切换到 CatBar；若出现阻断，可关闭开关回到旧入口且继续读取 v2 存档中的旧字段。
6. 完成自动化、视觉、性能和存档迁移验收后更新当前 specs 并归档 change。

## Open Questions

- 视觉基准分辨率、目标窗口尺寸和整数缩放倍率尚需在首个灰盒里最终锁定；建议先用 960×540 世界画布并兼容现有桌面窗口策略。
- 首发配方数量、真实品牌/虚构品牌命名和酒精内容分级尚未确定；建议纵向切片使用 2 个虚构酒液、冰块、1 种香料和 1 杯代表性配方。
- 手机打开时世界是否完全暂停尚未确定；本设计默认暂停玩家调酒输入但让卡座氛围以低频继续。
- 朋友圈照片最终采用像素插画、场景截图还是混合形式尚未确定；配表只保存图片稳定 ID，允许后续无代码替换。
- 参考图及未来素材的授权链需要用户确认；在确认前一律标记为 `placeholder`，不得作为发布资产。

## Context

CatBar 的业务调酒会话与粒子表现已经通过 `MixingVesselAdapter` 解耦，适配器内部复用 `CocktailShakerLab`。当前缺口不在求解器：实验场仍能产生带位置、速度和颜色的 `ParticleFluidSnapshot2D`；产品视图却把快照压缩成粒子数量后画成静态矩形，同时冰块也按固定槽位绘制。另一个缺口是场景控制器只暴露了程序调用的 `exit_mixing()`，调酒台 UI 没有退出请求，也没有处理 `ui_cancel`。送酒演员 `NekoDeliveryActor` 则把取杯、移动、放杯全部合并在一个角色中。

本变更跨越调酒表现、场景模式、服务演出、顾客配置和美术资产，但继续遵守 Godot 4.7.1、typed GDScript、功能目录和业务/粒子解耦约束。

## Goals / Non-Goals

**Goals:**

- 玩家可通过按钮或 `Esc` 从准备阶段安全返回大厅，并可再次进入干净会话。
- CatBar 杯内显示来自同一粒子求解器的实时局部粒子与冰块位置，Shake 与回稳期间都有可观察运动。
- 服务顺序明确为“调酒师放杯到吧台 → 打工猫取杯 → 送到卡座 → 结算”。
- 调酒师、打工猫和代表性顾客使用同一原创像素图集、统一比例和最近邻采样。
- 用自动化测试覆盖关键状态和事件顺序，并保持性能/稳定性门禁。

**Non-Goals:**

- 本轮不增加寻路网格、顾客点单 AI、多杯排队或失败送餐分支。
- 本轮不把视觉粒子反向用作配方剂量或结算依据。
- 本轮不制作完整八方向角色动画；先建立统一静态/状态姿势图集与可替换契约。

## Decisions

### 1. 调酒台发出退出意图，场景控制器拥有模式切换

`BartendingStation` 新增 `exit_requested` 信号、可见返回按钮和 `ui_cancel` 处理。调酒台只负责安全取消当前交互：结束指针捕获、取消勺子拖拽、停止 Shake、重置视觉和把会话置为取消；`CatBarController` 收到信号后调用现有相机/模式控制器返回全景。再次进入时由调酒台创建新会话并刷新活动订单。

这样保持 UI 不直接操作相机，也让退出按钮与键盘走同一路径。备选方案是在场景控制器全局监听 `Esc`，但会与手机等外围 UI 的返回语义冲突。

### 2. 公开“杯体局部只读快照”，产品视图只负责映射与绘制

`CocktailShakerLab` 新增只读查询，把世界坐标粒子转换成 Shake 杯局部米制坐标，并提供冰块局部位置、旋转、尺寸和颜色。`MixingVesselAdapter` 将这些数据复制到 `MixingVesselVisualSnapshot`；`ShakerVesselView` 按容器尺寸映射到本地像素并绘制粒子圆点/柔和液团和旋转冰块。

不把实验场整棵场景可见地嵌进 CatBar，也不访问流体核心的可写数组。这样两边共享相同求解结果，同时产品视图可以保持像素风和较低绘制预算。适配器在物理帧持续转发快照，避免只有鼠标事件到达时才更新回稳画面。

### 3. 服务演出拆成两个演员和一个显式吧台成品节点

保留 `NekoDeliveryActor` 作为调酒师，但职责收窄为从工作位移动到交接点、放下成品并发出 `drink_placed_on_bar`。新增 `WorkerCatDeliveryActor`，收到交接后前往吧台，发出取杯事件，再移动至配置卡座，放杯后发出唯一 `delivery_completed`。`CounterDrinkView` 在两个事件之间显示成品，确保玩家能看到“摆在吧台”的中间状态。

结算仅绑定打工猫的最终完成事件，现有 delivery key 继续提供幂等保护。即时测试模式同时加速两个演员，但仍保留完整事件顺序。

### 4. 单一角色图集加角色槽位配置

使用参考图的暖暗像素氛围重新创作透明 PNG 图集，固定四个等尺寸区域：调酒师、打工猫、夜猫客、下班猫。场景和 `PatronPrototype` 通过 `AtlasTexture`/`Texture2D` 配置选择区域，演员脚本只消费纹理和显示尺寸，不按角色 ID 写死路径。图集以 nearest、无 mipmap 的导入契约登记到资产清单，状态保持“生成式素材待发布审阅”。

选择单图集可以最大限度保证轮廓、色板和像素密度一致；未来可在不改稳定角色 ID 的情况下替换为同布局动画图集。

## Risks / Trade-offs

- [每物理帧复制粒子数组带来开销] → 使用现有 70 粒子产品预算，只复制只读快照，并以性能测试验证 16.67 ms 帧预算。
- [局部坐标映射与杯口方向不一致] → 映射以实验配置的杯宽/杯高为唯一尺度，并用边界测试验证所有粒子与冰块落在产品杯体内。
- [即时测试中的同步信号造成顺序难读] → 控制器公开阶段信号并在测试中记录事件数组，严格断言 `bartender_placed`、`worker_picked`、`delivered` 顺序。
- [生成图集可能存在不透明背景或格子不齐] → 生成后检查 alpha 与尺寸整除性，必要时再次透明化，并让资产校验拒绝不满足元数据的图集。
- [安全取消会丢弃当前未完成配料] → 这是现有规格定义的取消语义；按钮文案明确返回大厅，且只在成品提交前可用。

## Migration Plan

1. 先补失败回归测试与 OpenSpec 增量。
2. 增加只读流体/冰块局部快照和产品绘制，不改变业务会话数据。
3. 接通退出请求和重入新会话。
4. 增加打工猫与吧台成品节点，将结算回调迁移到最终送达。
5. 生成并登记统一图集，替换程序化角色主表现，保留缺图占位回退。
6. 运行 CatBar、流体、资产、性能、稳定性测试及截图检查。

回滚时可恢复旧演员接线和程序化占位绘制；业务存档字段与稳定订单 ID 均不变，无需存档迁移。

## Open Questions

- 后续角色动画是继续采用统一大图集，还是每个角色拆分独立动画资源；本轮通过 `Texture2D` 配置边界保留两种可能。
- 多杯并行订单和打工猫排队不在本轮范围，未来需要独立服务队列规格。
